# 구현 계획: 분실 신고 및 자동 후보 매칭

상태: 초안 (사용자 승인 대기)

## 명세 참조
- `specs/lost-report-matching/spec.md`

## 기술 맥락 및 제약
- Next.js 16 App Router, TypeScript, SQLite(`better-sqlite3`)를 사용한다.
- 기존 `lost_items` 테이블, 6개 카테고리, 텍스트 정규화 함수와 사진 저장·조회 기능을 재사용한다.
- 현재 사용자 계정이나 인증은 없다. 명세의 비공개 요구를 충족하려면 신고 소유권 증명이 필요하다.
- 매칭은 서버에서 날짜 전용 값으로 계산하고, 응답과 개인 신고 API는 캐시되지 않도록 한다.
- 구현은 단일 로컬 서버와 SQLite/로컬 사진 저장소를 대상으로 한다.

## 설계

### 분실 신고 데이터
- `lost_reports` 테이블을 추가한다.
- 필드: id, title, category, lost_date, location, optional description, optional photo_paths, owner_token_hash, created_at.
- 신고에는 공개 목록 API를 제공하지 않는다. 소유권 확인 없이 신고 데이터나 매칭 결과를 반환하지 않는다.
- 분실 사진은 기존 이미지 검증(최대 3장, JPG/PNG/WEBP, 장당 5 MB)과 저장 경로를 재사용한다.

### 소유권 증명 제안
- 각 신고에 대해 암호학적으로 안전한 256-bit 임의 토큰을 발급하고, 원문은 저장하지 않고 SHA-256 해시만 DB에 저장한다.
- 생성 요청 응답에 `HttpOnly`, `SameSite=Strict` 쿠키로 토큰을 설정하고, 쿠키 경로를 해당 신고 API로 제한한다. 운영 HTTPS에서는 `Secure`를 적용한다.
- 개인 신고 API는 쿠키 토큰의 해시와 해당 신고의 저장 해시를 상수 시간 비교 후 허용한다. 개인 응답에는 `Cache-Control: no-store`를 적용한다.
- 이 방식은 동일 브라우저의 비밀 쿠키를 소유권으로 사용하며 계정/기기 간 복구를 제공하지 않는다. 쿠키가 삭제되면 신고를 복구할 수 없다. 이 제약을 승인하지 않으면 구현 전에 계정 인증 방식을 별도로 결정한다.

### 후보 대상 및 점수 제안
- 후보 자격: 분실 신고와 카테고리가 같고, 습득 날짜가 분실 날짜 당일부터 30일 이내이며, 장소 부분 일치 또는 하나 이상의 공통 키워드가 있는 습득물.
- 텍스트는 기존 규칙대로 앞뒤 공백 제거, 연속 공백 축약, 영문 대소문자 비구분으로 정규화한다. 키워드는 물품명과 선택 특징 설명의 공백 구분 토큰으로 비교한다.
- 제안 점수: 날짜 가점 `30 - 경과 일수` (0~30), 장소 부분 일치 +20, 서로 다른 공통 키워드마다 +5 (최대 +30). 카테고리는 점수 가점이 아니라 필수 조건이다.
- 점수 내림차순, 날짜 간격 오름차순, 습득일 내림차순 순으로 정렬하고 최대 10건을 반환한다.
- 후보 카드는 썸네일, 제목, 습득 장소, 습득 날짜, 점수 및 매칭 근거를 표시한다. `후보 확인` 버튼은 해당 후보의 상세 정보를 모달로 보여주며 소유권 주장이나 수령 상태 변경은 하지 않는다.
- 점수 가중치, 후보 조건(장소 또는 키워드 중 하나 필수), 상한 10건은 제안이므로 사용자 승인 후 확정한다.

### API 및 화면
- `POST /api/lost-reports`: 필수값/사진을 검증하고 신고를 저장한 뒤 소유권 쿠키를 설정하고 즉시 후보 목록을 반환한다.
- `GET /api/lost-reports/[id]/matches`: 소유권 쿠키를 확인한 뒤 저장된 신고를 다시 매칭하고 후보 목록을 반환한다.
- 분실 신고 UI는 제출 후 신고 결과와 매칭 후보를 보여준다. 새로고침 후에도 같은 브라우저에서 비밀 쿠키를 이용해 결과를 다시 조회할 수 있게 한다.
- 후보가 없으면 명확한 빈 결과 상태를 표시한다. 알림은 발송하지 않는다.

## 인수 기준별 검증
- AC-1: 필수 입력, 선택 사진 및 기존 카테고리 선택을 UI/API 테스트로 확인한다.
- AC-2: 오늘 기본값, 과거 허용, 미래 거부를 UI와 서버 검증으로 테스트한다.
- AC-3: 신고 저장 후 기존 습득물 후보가 응답되는 데이터베이스 통합 테스트를 작성한다.
- AC-4: 카테고리 불일치, 날짜 범위 직전/시작/30일/31일 경계 테스트를 작성한다.
- AC-5: 승인된 각 가점, 합산, 내림차순과 동점 정렬 테스트를 작성한다.
- AC-6: 사진 유무, 매칭 정보와 후보 확인 모달을 컴포넌트 테스트로 확인한다.
- AC-7: 후보 0건의 빈 상태를 테스트한다.
- AC-8: 토큰 미제공, 잘못된 토큰, 다른 신고 토큰은 거부하고 올바른 소유자만 조회하는 API 테스트를 작성한다.
- AC-9: 요청 처리 중 푸시/이메일/문자 서비스가 호출되지 않음을 확인한다.
- AC-10: 각 누락 필드, 카테고리 오류, 날짜 오류의 비저장 및 사용자 수정 가능 오류를 테스트한다.

## 위험 및 대응
- 신고별 토큰은 계정이 아니다. 공유 기기에서는 브라우저 사용자가 바뀌어도 쿠키가 남을 수 있으므로 사용 후 로그아웃/신고 접근 해제 수단이 필요하다.
- 토큰 원문은 로그·DB에 남기지 않고 해시만 저장한다. HTTPS 운영에서 Secure 쿠키와 엄격한 쿠키 범위를 사용한다.
- 임의 사진 업로드, 동시 DB 쓰기, 부분 파일 저장은 기존 업로드 실패 정리 패턴을 재사용한다.
- 규칙 기반 매칭은 동의어/오탈자를 놓칠 수 있다. 이번 범위에서는 AI/OCR 없이 결정적 검색 규칙으로 처리하고, 오탐·미탐을 테스트 데이터로 확인한다.
- 날짜 범위를 달력 날짜로 계산해 시간대 차이로 30일 경계가 달라지지 않게 한다.

## 구현 순서
1. 소유자 토큰 방식과 제안 점수/후보 조건을 승인받는다.
2. SQLite 스키마와 분실 신고 데이터 모델·검증을 추가한다.
3. 분실 신고 저장 API, 사진 첨부 및 신고별 소유권 토큰을 구현한다.
4. 카테고리 게이트, 날짜 범위, 장소·키워드 가점 매칭 함수를 구현한다.
5. 소유자 전용 매칭 조회 API를 구현한다.
6. 분실 신고 폼과 비공개 제출 흐름을 구현한다.
7. 매칭 후보 목록, 상세 확인 모달, 결과 없음 상태를 구현한다.
8. 권한·경계·통합 테스트 및 전체 검사를 실행한다.
